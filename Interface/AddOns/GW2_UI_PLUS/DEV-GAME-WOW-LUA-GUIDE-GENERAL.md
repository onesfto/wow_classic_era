# 通用软件开发规范 - 魔兽世界经典怀旧服插件 (Lua)

本文档适用于新建魔兽世界（World of Warcraft）经典怀旧服（Classic Era，60 级）与硬汉模式（Hardcore）的 Lua 插件项目。这里的“通用”不是存量插件改造指南，而是新插件创建时的默认技术底座、工程纪律和边界规则，特别强调在硬汉模式下保证用户生命安全的苛刻要求。

除非用户或技术负责人在项目创建阶段明确批准例外，并写入项目自己的 `CLAUDE.md` 或等价规范，否则新项目按本文档默认标准执行。

## 一、核心设计原则

### 1. 代码结构与约束

- **短小精悍**：单文件保持短小，建议不超过 200 行，严格遵循单一职责原则。
- **防御性注释**：易碎、特殊、兼容性（正式服与怀旧服差异）或强业务约束逻辑必须通过注释划定修改边界。
- **绝不污染全局命名空间**：所有变量与函数必须声明为 `local`。插件自身的核心对象应封装在一个私有表中，通过 `AddonName, addonTable = ...` 方式在多个文件间共享。
- **最小实现**：不为未确认需求提前设计复杂的依赖库、配置系统或兼容分支。
- **零容错界面（硬汉模式）**：硬汉模式下角色死亡即刻删除，插件任何导致卡顿、报错、遮蔽视线的行为都是致命的。报错必须静默处理或记录至后台，严禁使用原生弹窗打断玩家操作。

### 2. 按特性分层（Feature-Sliced）

- **业务驱动划分**：插件代码必须按功能（如战斗日志解析、目标框体、背包管理）组织。
- **上下文收敛**：一个模块按需收敛该模块所需的事件注册、UI 框架与逻辑上下文。
- **模块边界清晰**：数据处理与视图渲染必须严格分离，避免在 `OnUpdate` 中进行重度逻辑计算。

### 3. 配置优于硬编码

- **数据持久化**：用户配置必须通过 `SavedVariables` 或 `SavedVariablesPerCharacter` 管理。
- **禁止魔法数值**：严禁随意使用硬编码的法术 ID 或物品 ID，必须统一在常量模块中管理，并附带注释说明法术名称。

### 4. 最小化与一致性

- **保持统一**：插件内的事件监听风格、错误处理和 UI 交互必须统一。
- **先沟通再扩展**：需求不清晰时，必须先沟通澄清，避免过度设计。

## 二、技术栈约束分层

以下规则用于区分必须遵守的工程底线、默认推荐的技术选型和可由项目决定的约定。

- **必须：语言与环境**：新项目默认使用 `Lua 5.1`（魔兽世界客户端标准）；必须使用 `WOW_PROJECT_ID == WOW_PROJECT_CLASSIC` 进行环境判定，而非依赖版本号。
- **必须：污染追踪（Taint Tracking）**：任何涉及原生 UI 的修改，必须开启 `/console taintLog 1` 进行测试，验证是否导致暴雪原生框架被污染而无法在战斗中点击。
- **必须：防御性编程**：任何 API 调用前，必须检查返回值的有效性，对未知数据结构进行 `type()` 检查或 nil 检查。
- **必须：事件节流**：必须对 `OnUpdate` 进行严格节流。如非必须，帧率控制在 0.1 秒至 0.5 秒一次，绝不可按帧执行重度循环。
- **默认推荐：第三方库**：如果仅需少量功能，禁止引入重型框架（如全套 Ace3）。优先使用原生 API 或轻量级模块（如 LibStub）以减少加载负担和潜在冲突。
- **项目约定：调试工具**：开发阶段推荐封装统一的 `print` 输出或接入 BugSack/BugGrabber 进行报错捕获。

## 三、项目与目录结构规范

### 1. 推荐目录树视图

插件目录默认遵循以下结构划分。业务模块可以按实际业务增减目录，但职责边界不能改变。

```text
MyHardcoreAddon/
├── MyHardcoreAddon.toc           # 插件清单文件（必须）
├── CLAUDE.md                     # AI 全局生成规范与系统提示词约束
├── Embeds.xml                    # 第三方依赖库加载清单（可选）
├── Assets/                       # 静态资源（材质、字体、声音）
│   ├── Fonts/
│   ├── Textures/
│   └── Sounds/
├── Libs/                         # 第三方依赖库
│   ├── LibStub/
│   └── CallbackHandler-1.0/
├── Locales/                      # 多语言本地化文件
│   ├── enUS.lua
│   └── zhCN.lua
├── Core/                         # 核心初始化与事件分发
│   ├── Init.lua
│   └── Constants.lua             # 全局常量（法术ID、枚举等）
├── Modules/                      # 业务切片层（按功能划分）
│   ├── CombatLog/                # 战斗日志分析模块
│   └── WarningUI/                # 危险预警界面模块
└── UI/                           # 全局共享界面模板与组件
    ├── Templates.xml
    └── MainFrame.lua
```

### 2. 核心目录精确编写规范

- **`MyHardcoreAddon.toc`（插件清单）**
  - 必须包含标准元数据，明确标注 `## Interface: 11500`（或当前经典服版本号）。
  - 必须声明正确的 `## OptionalDeps` 与 `## SavedVariables`。
- **`Assets/`（静态资源）**
  - 存放所有图片（`.blp` 或 `.tga`）、字体（`.ttf`）和音效（`.ogg` 或 `.mp3`）。
  - 引用路径必须相对插件根目录，例如 `Interface\\AddOns\\MyHardcoreAddon\\Assets\\Textures\\icon.blp`。
- **`Libs/`（第三方依赖库）**
  - 将所有外部库（如 Ace3 组件、LibStub 等）存放在此目录。
  - 必须在 `Embeds.xml` 或 `.toc` 文件中按正确的依赖顺序加载。
- **`Core/`（核心初始化）**
  - 负责插件的生命周期事件（`ADDON_LOADED`, `PLAYER_LOGIN`）监听与模块调度。
- **`Modules/`（业务切片层）**
  - 必须严格监控事件注册。离开特定场景时，必须立即释放（`UnregisterEvent`）无用事件。
  - 经典服光环 API 差异：必须使用 `UnitAura` 或 `UnitBuff`、`UnitDebuff`，并注意其索引方式与返回值变化。
- **`UI/`（界面层）**
  - 宏与保护功能限制：若需创建可点击的施法按钮（SecureActionButtonTemplate），必须在非战斗状态下完成初始化，严禁在战斗中动态修改宏文本或施法目标。

## 四、编码与架构规范

### 1. 内存与垃圾回收优化

- **禁止高频创建表**：内存控制是硬汉模式性能的关键。严禁在 `OnUpdate` 或高频事件（如 `COMBAT_LOG_EVENT_UNFILTERED`）中频繁创建临时表。必须复用已有表并使用 `wipe(table)` 清理数据。
- **字符串拼接限制**：在循环中避免大量使用 `..` 进行字符串拼接，优先使用 `string.format` 或表合并（`table.concat`）。

### 2. 战斗与预警逻辑

- **战斗日志解析**：解析战斗事件时，必须通过 `CombatLogGetCurrentEventInfo()` 获取参数。
- **高优先级预警**：硬汉插件需对生命值突降、高危目标（如精英怪、巡逻怪）、网络延迟做出极高优先级的视觉或听觉反馈。
- **脱战状态判定**：对于脱战状态（`PLAYER_REGEN_ENABLED`）的检测必须精准，以支持玩家安全登出或规划逃生。

## 五、全局命名与工程硬性规范

### 1. 命名与前缀

- **避免全局冲突**：如果必须创建全局变量（如 Slash 命令、全局框架名），必须以插件简写为前缀（例如 `MYHC_MainFrame`）。
- **文件与目录命名**：目录及文件首字母大写（PascalCase），例如 `MainFrame.lua`。

### 2. 环境与部署

- **本地测试环境**：必须在极端环境（如主城满屏玩家、40 人团队）下测试内存占用与帧数影响。
- **断线与重载恢复**：针对硬汉模式，必须建立网络断线恢复、重载界面（`/reload`）后的状态恢复机制，确保重载不会导致战斗中数据丢失或状态紊乱。
- **发布构建**：正式发布前必须清理调试代码与高频日志输出，确保压缩包目录结构与 TOC 文件名绝对一致。
